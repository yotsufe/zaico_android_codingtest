# コミット分割して PR を作成する

## 全体の流れ

```
ブランチを切る                           ← 実装より前。この Skill の管轄外だが下記参照
 → 実装
 → peer-review（別エージェントによるレビュー）   ← ここからがこの Skill（§2 で呼ぶ）
 → 指摘を反映
 → ブランチ確認 → 検証（ビルド / テスト / Lint / 秘密情報）
 → ユーザーがレビュー                    ← 必ず止まる。唯一のゲート
 → コミット分割
 → push → PR 作成 → 結果を報告           ← ここで終わり
```

**ユーザー確認はコミットより前に 1 回だけ置く。** 作業ツリーの変更なら
直すだけで済み、履歴の作り直しが要らない。最も安い時点で見てもらう。

**「PR まで作って」のような事前の指示は、このゲートの承認ではない。**
その時点ではまだ peer-review をしていないので、ユーザーは指摘を見ずに承認することになる。
実装を終えたら必ず peer-review を通し、**その結果を添えて改めてレビューを依頼する**。

実際にこの順序を崩して、`pipefail` の下で `grep -q` がマーカーを誤って削除するという
重大な指摘が出た変更を、ユーザーが最終差分を見ないまま push したことがある。

**事前の指示は §1〜§4 を進めてよいという承認**として扱う。§5 で改めて止まり、
そこから先（コミット・push・PR 作成）の承認を得る。§5 の手前で別のゲートを置かない。

このゲートで得る承認は、**コミット分割から PR 作成までの全体**に対するもの。
承認後は途中で止まらずに進め、最後に結果（PR の URL とコミット構成）を報告する。

## ブランチは実装より前に切る

**実装を始める前に、最新の `main` からブランチを切る。**

```bash
git checkout main && git pull && git checkout -b <branch>
```

作業ツリーがクリーンなうちに `main` の鮮度を確認できるのが要点。
実装後に切ろうとすると、**未コミットの変更を抱えたまま `fetch` や `rebase` をする**
羽目になり、`main` に直接コミットしてしまう事故も起きる。

ブランチ名は実装前に仮決めでよい。後から `git branch -m <新しい名前>` で変えられる。

この Skill は実装後に呼ばれるので、ブランチ作成そのものは管轄外。
ただし切られていなかった場合の救済を §3 で扱う。

---

コミットはこの Skill が明示的に呼ばれたときに限って行う。
**このリポジトリでは、ユーザーの明示的な指示なしにコミットしてはならない。**
「実装が終わったから」といった状態を理由に自動で起動しないこと。

**PR 作成後（CI 確認、レビュー指摘への対応、マージ、ブランチ削除）はこの Skill の対象外。**

## hook による強制

以下は `.claude/settings.json` の PreToolUse フック（`.claude/hooks/git-guard.sh`）が
機械的に拒否する。

| 拒否されるもの | 対応する手順 |
|---|---|
| `--force` / `-f` / `--force-with-lease` つきの `git push` | §7 |
| **peer-review を通していないブランチの `git push` / `gh pr create`** | **§2** |
| detached HEAD からの `git push`（ブランチ名でマーカーを引けないため） | **§2** |
| 秘密情報を含むコミットの `git push` | §4-1 / §7-1 |

`main` への直接コミットは hook では止めない。ブランチ先行は §3 の手順で扱う
（`main` 上にいると気づいたら §5 でユーザーに確認する）。

**hook は完全な防壁ではない。** シェルコマンドを正規表現で読むだけなので、
変数展開（`g=push; git $g`）や多段のインタプリタ経由は原理的に検知できない。
秘密情報の判定もパターンマッチなので、未知の形式は素通りする。

**hook があるからといって、この手順の検証を省略しない。** hook は最後の砦であって、
手順の代わりではない。hook に拒否された時点で気づくのでは、コミットを作り直す
手戻りが発生する。秘密情報は §4-1 の時点で見つけるのが本来。

hook に拒否されたら、**回避しようとせず止まってユーザーに報告する。**

## 用語

- `<scratchpad>` — セッションのスクラッチパッドディレクトリ（システムプロンプトに示されるもの）
- `<branch>` — これから作るブランチ名
- `<package>` — `app/build.gradle.kts` の `applicationId`

## 1. 事前チェック

```bash
git branch --show-current
git status --short
git rev-list --count main..HEAD    # main より進んでいるコミット数
git remote -v
gh auth status
```

### 何をするかの判定

| 状態 | すること |
|---|---|
| 作業ツリーに変更あり | 通常どおり §2 へ |
| 作業ツリーはクリーンで `main..HEAD` が 0 | **やることなし。** その旨を伝えて終了 |
| 作業ツリーはクリーンで `main..HEAD` が 1 以上 | **コミット済みで push 前の再開。** §4（検証）と §5（ユーザー確認）は飛ばさずに実施し、§6 を飛ばして §7 へ |

再開時に §2 の peer-review で指摘が出た場合、修正は作業ツリーに残る。
**そのときは §6 を飛ばさない。** 飛ばすと修正をコミットする節が無く、
§7-1 の「作業ツリーがクリーンであること」で必ず落ちる。

「変更がないから終了」と即断しない。**コミット済みで push だけ残っている状態**は
中断・再開時に普通に起きる。ここで誤終了すると PR が永久に作られない。

再開時も §4 と §5 は飛ばさない。§7-1 が §4-1 で決めた検索語を使うため、
飛ばすと参照先が無くなる。またユーザーの承認を得ないまま push することになる。

`gh pr list --head <branch>` で既に PR があるかも確認する。あれば新規作成しない。

## 2. peer-review を通す

このセッションで実行済みかどうかを確信できないなら、**実行する**。
重複実行のコストより、未レビューのままコミットするリスクのほうが大きい。

**これは hook で強制される。** `.claude/peer-review/<ブランチ名の / を ~ にしたもの>` が
無いと `git push` も `gh pr create` も拒否される。飛ばすならユーザーに確認したうえで、
理由をマーカーに記録すること（黙って飛ばさない）。

**ブランチを切り直す・改名するときはマーカーも持ち越す。** マーカーはブランチ名で引くので、
§3 ケース2（`main` 上でレビューしてからブランチを切る）やケース3、`git branch -m` の後は
そのままだと §7 の push で拒否される。

```bash
mv ".claude/peer-review/$(git symbolic-ref -q --short HEAD | tr '/' '~')" \
   ".claude/peer-review/<新しいブランチ名の / を ~ にしたもの>"
```

`peer-review` は指摘を反映したうえで返す。判断を仰ぐ指摘（設計の選択を伴うもの）が
含まれていたら、ユーザーに決めてもらってから §3 へ進む。

これは §5 のゲートとは別の停止点だが、**コミット前に内容を確定させるための確認**であり、
「コミットしてよいか」を問うものではない。設計の選択が残ったまま §5 に進むと、
ユーザーは決めきれない状態でコミットと push を承認することになる。

## 3. ブランチを確認する

```bash
git branch --show-current
git fetch origin main
git rev-list --count main..origin/main    # ローカル main が origin より遅れている数
```

### ケース1: フィーチャーブランチ上にいる（想定どおり）

ブランチ作成は済んでいるので、**何もせず §4 へ進む。**

ただしローカル `main` が `origin/main` より遅れている場合は、
`main..HEAD` を基準にした差分表示や秘密情報スキャンが古い土台を基準にするため、
**その旨をユーザーに伝えてから進む**（rebase するかはユーザーが判断する）。

### ケース2: `main` 上にいる（ブランチを切り忘れている）

ここでは**まだブランチを切らない。** 以下を決めて、§5 の確認事項に含める。

- `main` 上で作業してしまっていること
- 変更内容から提案するブランチ名
- ローカル `main` が `origin/main` より遅れているかどうか

ゲートを 2 回に増やさないため、承認は §5 でまとめて得る。
承認後、§6 の冒頭で以下を実行する。

```bash
git checkout -b <branch>        # main から切る。未コミット変更はそのまま移る
```

**`git checkout main` を挟まない。** 既に `main` にいるので不要で、
遅れている `main` を `pull` しようとすると未コミット変更と衝突する。
`main` の更新が必要ならユーザーの判断を仰ぐ。

checkout が失敗した場合（`main` と衝突する変更がある）は、そこで止まって報告する。

### ケース3: 同名のブランチが既に存在する

`git rev-parse --verify <branch>` が成功する場合は、別の名前を用意し、
**§5 でその旨を伝える。** 既存ブランチを上書きしない。

### 共通

**主題の異なる変更を同じブランチに混ぜない。** 別の話題が混ざっていることに
気づいたら、その時点でユーザーに分けるかどうかを確認する。

## 4. 検証

この時点ではまだコミットしていない。**作業ツリーの状態**を検証する。

**全部通ってから**ユーザーに確認を依頼する。1 つでも落ちたら、直すか報告するかを判断する。

### 4-1. 秘密情報スキャン

**検索語を先に決める。** 以下を列挙して 1 つの正規表現にまとめる。

- この変更で扱った秘密情報の**実値**（`local.properties` の値、リソースに書かれたトークンなど）
- 汎用パターン: `Bearer [A-Za-z0-9]`, `api[_-]?key`, `secret`, `password`, `token\s*=`, `-----BEGIN`

実値を毎回書くのが面倒なら `.claude/hooks/secret-patterns.txt` に 1 行 1 正規表現で
登録しておく。hook がそれも使って検査する（このファイルは `.gitignore` 対象）。

```bash
PAT='<上で決めた正規表現>'

# 作業ツリー（追跡ファイル）
git grep -l -E "$PAT" --

# 未追跡ファイル
git ls-files --others --exclude-standard -z | xargs -0 /usr/bin/grep -lE "$PAT"

# 既存のコミット（再開時。rev-list が空だと git grep は作業ツリー検索に化けるのでガードする）
REVS=$(git rev-list main..HEAD)
if [ -n "$REVS" ]; then git grep -l -E "$PAT" $REVS -- ; fi
```

コミット後にもう一度走らせる（§7）。PR 本文もそのときスキャンする。

**検出したら、その場で止めてユーザーに報告する。** 独断で履歴を書き換えない
（`filter-branch`、`rebase`、`--amend` のいずれも）。除去方法はユーザーに決めてもらう。

`grep -r` はこの環境では `.gitignore` を尊重する（`grep` が
`~/.claude/shell-snapshots/` のシェル関数で上書きされているため。`/usr/bin/grep` は尊重しない）。
無視ファイルを見落とすので、追跡対象の検査は必ず git ベースで行う。

### 4-2. ビルド・テスト・Lint

```bash
./gradlew :app:assembleDebug          # BUILD SUCCESSFUL を目視確認
./gradlew :app:testDebugUnitTest      # app/src/test に実テストがある場合
./gradlew :app:lintDebug              # アクセシビリティ・多言語対応・API 互換はここで見る
```

Lint はアクセシビリティや `contentDescription` 欠落、ハードコード文字列を
機械的かつ高精度に検出する。レビュー観点として人手やエージェントを当てるより確実。

### 4-3. 変更内容の把握

ユーザーに提示するための材料を集める。

```bash
git status --short
git diff --stat                       # 未ステージ
git diff --cached --stat              # ステージ済み
git ls-files --others --exclude-standard   # 未追跡（新規ファイル）
```

## 5. ユーザーに確認を依頼する

**ここで止まる。この Skill で唯一のゲート。**

**事前に「PR まで」と言われていても、ここで必ず止まる。** peer-review の結果を見せずに
先へ進めない。

§2 でユーザーの了承を得て peer-review を飛ばした場合は、結果の代わりに
**飛ばしたこと・その理由・了承を得た経緯**を提示する。飛ばした事実を伏せない。

まだコミットしていないので、直すのが最も安い時点。以下を提示する。

- **peer-review の結果**。起動した観点、指摘の件数、反映した内容、落とした指摘と理由、
  **実行できなかった観点があればその旨**（観点が落ちたままゲートを通さない）
- **変更内容**。何をどう変えたか。ファイル一覧だけでなく、判断を伴った箇所は理由も
- 差分統計（変更ファイル数、増減行数）
- 検証結果（§4-1〜4-3）
- **これから作るコミットの分割案**（何を何コミットに分け、なぜそう分けるか）
- PR のベースブランチ（通常 `main`）と Draft かどうか
- **§3 で異常を検出していればその内容**（`main` 上で作業している、`main` が遅れている、
  ブランチ名が衝突している）と、どう対処するかの提案

**この承認で、コミット分割から PR 作成までの全体を進めてよいことになる。**
承認が得られたら §6 以降は止まらずに進め、最後に結果を報告する。

そのため、**確認を依頼する時点で「この後 push して PR を作る」ことを明示する。**
「コミットしてよいか」だけを聞いて push まで進めない。

コミットの分け方そのものはユーザーが事前に見られないので、
§6 の分割方針を厳密に守り、結果は §7 の報告で必ず見せる。

## 6. コミットを分割する

§3 がケース2 だった場合は、まずここでブランチを切る（`git checkout -b <branch>`）。

### 方針

**性質ごとに分ける。1 コミットが 1 つのことだけをする。**

- `chore:` 設定ファイル、`.gitignore` などのノイズ。**先に片付ける**
- `fix:` / `feat:` 本題
- 独立して読めるもの（例: 秘密情報の管理方法の変更）は別コミットにする

**各コミットは単体でビルドが通ること。** これを守るため、途中の状態を作り直す場合がある。

### 中間状態の作り方

退避は **git の中**で行う。スクラッチパッドへの `cp` は使わない
（ディレクトリ構造が潰れる、セッションが切れると失われる、中断時に復旧できない）。

```bash
# 1. 最終状態を一時コミットにして退避し、すぐコミットだけ取り消す
#    （タグが指すのでオブジェクトは残る。作業ツリーは最終状態のまま）
git add -A && git commit -q -m "wip: 最終状態" && git tag -f wip/final && git reset -q --mixed HEAD~1
git rev-parse --short wip/final         # 退避できたことを確認

# 2. 中間状態を書く → ビルド確認 → コミット
./gradlew :app:assembleDebug            # BUILD SUCCESSFUL を目視確認
git add -A <paths> && git commit -F - <<'EOF'
...
EOF

# 3. 最終状態に戻す
#    先に「中間状態だけに存在するファイル」を消してから戻す
git diff --name-only --diff-filter=A wip/final HEAD | xargs -r rm -f
git checkout wip/final -- .
git diff wip/final --name-only          # 空であること（＝最終状態と一致）
./gradlew :app:assembleDebug
git add -A && git commit -F - <<'EOF'
...
EOF

# 4. 後始末
git tag -d wip/final
```

**なぜこの形か（いずれも実測で確認済み）:**

- **`git stash create` は使わない。** `-u` を付けても未追跡ファイルは `stash^3` に入り、
  `git checkout <stash> -- .` では**復元されない**。一時コミットなら `git add -A` で
  すべて追跡されるため確実に戻る。また `stash create` は作業ツリーがクリーンだと
  空文字を返し、ガードしないと退避できていないまま次へ進む
- **`git checkout wip/final -- .` は退避に無いファイルを削除しない。**
  中間状態で追加したファイルが最終状態に残り込むため、先に
  `--diff-filter=A` で洗い出して消す
- **スクラッチパッドへの `cp` は使わない。** ディレクトリ構造が潰れ、
  同名ファイル（`build.gradle.kts` がルートと `app/` に等）が静かに上書きされる。
  セッションが切れると失われ、中断時に復旧できない

**中断からの復旧**: `wip/final` タグが残っていれば `git checkout wip/final -- .` で
最終状態を取り戻せる。タグが残ったまま作業が終わっていたら復元漏れなので確認する。

### ビルド確認の落とし穴

- `./gradlew ... -q 2>&1 | tail` は **`tail` の終了コードを拾う**ため、
  失敗しても成功に見える。`BUILD SUCCESSFUL` の文字列で判定すること
- 生成コード（`BuildConfig` など）の有無が変わる中間状態では、
  インクリメンタルビルドの残骸で 1 回目が失敗することがある。再実行して確認する

### コミットメッセージ

日本語。1 行目は `<type>: <何をしたか>`。本文は以下の構成にする。

```
## 問題      何が起きていたか（ログ・エラーメッセージを引用する）
## 原因      なぜそうなったか（実際に叩いた API のレスポンスなど、根拠を示す）
## 対応      何をしたか。判断を伴うものは理由も書く
## 確認      どう検証したか
```

小さな変更（`.gitignore` など）は `## 問題` などを省いて数行でよい。

末尾に必ず付ける:

```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

## 7. push と PR 作成

§5 で承認済みなので、ここでは止まらない。

### 7-1. コミット後の最終確認

コミットによって秘密情報が履歴に入っていないか、もう一度確認する。
§4-1 は作業ツリーしか見ていない。

```bash
PAT='<§4-1 と同じ正規表現>'

REVS=$(git rev-list main..HEAD)
if [ -z "$REVS" ]; then
  echo "対象コミットなし。ブランチの分岐を見直すこと"
else
  git grep -l -E "$PAT" $REVS -- ; echo "  (出力なし = 検出なし)"
fi

# PR 本文（ログやレスポンスを貼るため混入しやすい）
/usr/bin/grep -nE "$PAT" <scratchpad>/pr_body.md

git status --short                    # クリーンであること
./gradlew :app:assembleDebug          # 最終状態でビルドが通ること
```

**検出したら push しない。** 止まってユーザーに報告する。

### 7-2. push と PR 作成

```bash
git push -u origin <branch>

# Draft かどうかで分岐（§5 で確認した結果に従う）
gh pr create --base main --head <branch> --title "<件名>" --body-file <scratchpad>/pr_body.md
# Draft の場合は --draft を付ける

# 番号は現在のブランチから引ける（引数なしで現ブランチの PR を見る）
gh pr view --json number,title,state,baseRefName,headRefName,isDraft,additions,deletions,changedFiles,commits
```

### 7-3. 結果を報告する

ユーザーはコミットの分け方を事前に見ていないので、**必ず見せる。**

```bash
git log --reverse --format="%n● %h %s" --name-status main..HEAD
git diff --stat main..HEAD
```

報告に含めるもの:

- PR の URL と状態
- **コミット構成（ハッシュ・件名・変更ファイル数）と、そう分けた理由**
- 検証結果
- 構成に不満があれば、追加コミットかマージ時の squash で調整できること

### 失敗したとき

- **push が reject された**（非 fast-forward）— **force push は禁止。**
  `--force` も `--force-with-lease` も使わない。止まってユーザーに報告し、指示を仰ぐ
- **`gh pr create` が「already exists」** — 既に PR がある。新規作成せず `gh pr view` で
  既存 PR を確認し、ユーザーに報告する

**push 後に修正が必要になった場合は、追加コミットで対応する。**
履歴を書き換えない。人間がレビューしている最中に履歴が変わると、
前回からの差分が追えなくなり、レビューコメントの紐付きも切れる。
履歴の見た目はマージ時の squash で担保する。

### PR 本文の構成

**人間がレビューしやすいこと**を最優先にする。

```markdown
## 概要
何を解決したか。1〜2 文で言い切る。
コミットの一覧を表にして、どれが本題かを示す。

## 何が起きていたか
エラーログをそのまま引用する。

## 原因
根拠を示す。API が絡むなら実際のリクエストとレスポンスを載せる。

## 対応
変更前後を表で比較する。判断を伴うものは理由を書く。
> 引用ブロックで補足を入れると読みやすい。

## 動作確認
セットアップ手順と、チェックボックスで確認項目。

## レビュー観点
**自分が判断で決めた箇所を明示する。** 他の選択肢があったものは特に。
レビュアーが異論を出しやすくなる。

## スコープ外
やっていないことと、その理由。次にやることへの言及。
```

ログやレスポンスを貼る箇所は、**§7-1 の秘密情報スキャンを必ず通す。**

末尾に付ける:

```
🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

---

## 注意

- **自分の変更と無関係なファイルを巻き込まない。** 差分がノイズで埋まるとレビューが機能しなくなる
- 実機での確認が必要な変更は、`adb` で E2E を通してから PR にする

  ```bash
  adb devices                   # 先に接続確認。切断されているとコマンドが長時間ハングする
  adb logcat -c -b crash
  adb install -r app/build/outputs/apk/debug/app-debug.apk
  adb shell am start -n <package>/.MainActivity
  adb logcat -d -b crash        # 空であること
  adb shell screencap -p /sdcard/s.png && adb pull /sdcard/s.png <scratchpad>/
  ```

  `sleep` はこの環境で使えない
- **画面が表示されたことの確認は、プロセスの生存ではなくスクリーンショットで行う。**
  端末がロック画面だと Activity が resume していても何も見えない
