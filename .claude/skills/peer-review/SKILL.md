# 別エージェントによるレビュー

実装した本人（＝直前までコードを書いていた自分）は、自分が下した判断を正当化する方向に偏る。
なぜその設計にしたかを知っているぶん、他の選択肢が見えなくなる。

独立したエージェントに、**実装の経緯を伝えずコードだけを見せて**レビューさせる。

## 組み込み Skill との使い分け

| | 使う場面 |
|---|---|
| **この Skill** | 観点ごとに分担させて並列にレビューしたいとき。PR を作る前 |
| 組み込み `code-review` | 差分に対する通常のレビュー。単に「レビューして」と言われたとき |
| 組み込み `security-review` | 秘密情報・脆弱性が主たる関心事のとき |

秘密情報の混入チェックはこの Skill の観点に含めない。必要なら `security-review` を使う。
なお `pr-create` は push 前に独自の秘密情報スキャンを行うので、そちらの経路では別途不要。

## 手順

### 1. レビュー対象を確定する

**3 つの状態の和集合**を取る。どれか 1 つだけでは必ず漏れる。

```bash
git diff main...HEAD --name-only     # コミット済み（ブランチを切っている場合のみ）
git diff --name-only                 # 未ステージ
git diff --cached --name-only        # ステージ済み
git ls-files --others --exclude-standard   # 未追跡（新規ファイル）
```

`git diff` 系は**未追跡ファイルを出力しない**。新規ファイルこそレビューが必要なので、
`git ls-files --others` を必ず併用する。

フィーチャーブランチ上で実装していれば `main...HEAD` にコミット済みの変更が、
作業ツリーに未コミットの変更がそれぞれ入る。**どちらか一方だけを見ない。**
`main` 上で作業してしまっている場合は `main...HEAD` が空になるので、
それを「対象 0 件」と誤判定しないこと。

4 つすべてが空のときだけ「対象なし」と判断し、その旨を伝えて終了する。

### 2. 観点を選ぶ

**変更内容に応じて選ぶ。「いつ選ぶか」列に該当しないものは起動しない。**

| 観点 | いつ選ぶか | 見るもの |
|---|---|---|
| **正しさ・異常系** | 常に | null 安全、例外の伝播経路、外部データの形式が想定と違う場合、境界値、**失敗時・読み込み中・0 件時にユーザーに何が表示されるか** |
| **ライフサイクル・非同期** | 画面・通信・並行処理に触れたとき | Fragment / Activity のライフサイクル、リソースやリスナーのリーク、画面回転、**コルーチンスコープの選択（`GlobalScope` を使っていないか）、キャンセル伝播、Dispatcher、`runBlocking` の使用** |
| **言語のイディオム** | 常に | `!!` の使用、スコープ関数の乱用、命名、可読性 |
| **設計・責務分割** | 新規クラス追加、責務の移動があったとき | 責務が適切に分かれているか、重複がないか、テスト可能な形になっているか |
| **テストの質** | ロジックを追加・変更したとき | 異常系（通信失敗・不正データ）が検証されているか、実装の写経になっていないか、外部依存をモックできているか、そもそも書かれているか |
| **ビルド設定・依存** | `build.gradle.kts` / `libs.versions.toml` に変更があるとき | バージョンの乖離・重複定義、version catalog を迂回した直書き、不要な依存、ライセンス、難読化時の影響 |

常時起動は「正しさ・異常系」「言語のイディオム」の 2 つだけ。
他は該当するときのみ。**観点を増やすほどコストが上がり、指摘の質は下がる。**

### 3. エージェントを並列で起動する

**1 メッセージ内で複数の Agent を同時に呼ぶ。** 逐次実行しない。

`subagent_type` は読み取り専用の **`Explore`** を使う。
`general-purpose` は Write / Edit を持つため、**並列で同じ作業ツリーを書き換える恐れ**がある。
やむを得ず `general-purpose` を使う場合は、プロンプトに「ファイルを変更するな」を明記する。

各エージェントに渡すもの:

- 対象ファイルのパス。**差分ではなくファイル全体を読ませる**（周辺コードとの整合を見てもらうため）
- そのエージェントが担当する観点
- どこが今回の変更範囲かは伝える（変更と無関係な既存コードの指摘を抑えるため）
- 「**確信のある指摘のみ**を、`file_path:line_number` つきで返す。憶測や好みの問題は書かない」

**渡してはいけないもの:**

- なぜその実装にしたかの理由
- 検討した末に却下した代替案
- 「ここは意図的にこうしている」といった弁明

これらを渡すと、エージェントは追認するだけになる。

### 4. 指摘を統合する

- **各観点の実行成否をまず確認する。** エージェントが落ちて結果が返らなかったのか、
  本当に指摘ゼロだったのかを区別する。落ちた観点は再実行するか、落ちたことを明示する
- 重複を除く
- **重要度順**に並べる（クラッシュ・データ破損 > 設計上の問題 > 可読性）
- 各指摘に `file_path:line_number` を添える
- **エージェントの指摘を鵜呑みにしない。** 事実かどうかを自分で確かめる。
  コマンドで検証できるものは実際に動かして確かめる。
  誤りや的外れなものは、そう判断した理由とともに落とす

### 5. 指摘を反映する

**落とさなかった指摘は、原則すべて修正してから報告する。**

ただし以下は修正せず、報告して判断を仰ぐ:

- **どの設計を採るかの選択を伴うもの**（A 案と B 案があり、どちらも成立する）
- **ユーザーの方針に関わるもの**（何を許可するか、どこまでを対象に含めるか）
- 修正の影響範囲が、今回の変更の枠を超えるもの

### 6. 報告する

- 修正した指摘（何をどう直したか）
- 判断を仰ぐ指摘（選択肢と、推奨）
- **落とした指摘と、落とした理由**
- 実行できなかった観点があればその旨

### 7. 実施を記録する

**報告まで終えたら、最後に必ずマーカーを書く。**

```bash
mkdir -p .claude/peer-review
# / は ~ に置き換える。git はブランチ名に ~ を許さないので、_ と違って
# feat/x と feat_x が同じファイル名に潰れる衝突が起きない。
BRANCH=$(git symbolic-ref -q --short HEAD | tr '/' '~')
cat > ".claude/peer-review/$BRANCH" <<EOF
reviewed: $(git rev-parse HEAD)
観点: <起動した観点をカンマ区切りで>
指摘: <件数>（修正 <件数> / 判断待ち <件数> / 却下 <件数>）
EOF
```

`.claude/hooks/git-guard.sh` がこのファイルを見て、**マーカーが無いブランチの
`git push` と `gh pr create` を拒否する**。レビューを飛ばしたまま PR を出すのを防ぐため。

`reviewed:` の SHA は人が読むための記録で、hook は**存在の有無しか見ない**。
`pr-create` の流れではレビューの後にコミットを作るため、この SHA は push 時の HEAD とは
一致しない。「いつ時点のツリーを見たか」を後から辿るためだけに残している。

レビューを飛ばす場合は、同じ場所に理由を書く。**書式は 1 行目を `SKIPPED:` で始める。**

```bash
echo 'SKIPPED: <理由。ユーザーの了承を得たことを含める>' > ".claude/peer-review/$BRANCH"
```

このディレクトリは `.gitignore` 対象なので、リポジトリには入らない。

### 8. 古いマーカーを掃除する

**マーカーを書いたついでに、消えたブランチのものを片付ける。**

```bash
KEEP=$(git for-each-ref --format='%(refname:short)' refs/heads | tr '/' '~')
if [ -n "$KEEP" ]; then                     # 空なら何も消さない（全消しを防ぐ）
  for f in .claude/peer-review/*; do
    [ -f "$f" ] || continue
    # grep -q は一致した時点で終了し、上流の printf が SIGPIPE で死ぬ。
    # pipefail の下では終了ステータスが 141 になり、一致したのに消してしまう。
    printf '%s\n' "$KEEP" | /usr/bin/grep -xF "${f##*/}" >/dev/null || rm -f "$f"
  done
fi
```

**hook では掃除しない。** 検査用のフックが副作用でファイルを消すと、拒否するだけの場合でも
状態が変わり、`SKIPPED:` の記録が失われる。

## 注意

- 指摘の**件数だけ**を伝えて終わらせない。中身がわかる形で出す
- 指摘ゼロなら「ゼロだった」と明言する。無理に何か挙げない
- 修正は作業ツリーに残す。コミットは `pr-create` の管轄
