# 別エージェントによるレビュー

実装した本人（＝直前までコードを書いていた自分）は、自分が下した判断を正当化する方向に偏る。
なぜその設計にしたかを知っているぶん、他の選択肢が見えなくなる。

独立したエージェントに、**実装の経緯を伝えずコードだけを見せて**レビューさせる。

## 使いどころ

- 実装が一段落し、ユーザーに確認を依頼する**前**
- `pr-create` で PR を作る**前**（`pr-create` はこの Skill を呼ぶ）

## 手順

### 1. レビュー対象を確定する

```bash
git status --short
git diff main...HEAD --stat      # ブランチ作成済みの場合
git diff --stat                  # 作業ツリーのみの場合
```

対象が 0 件なら、その旨を伝えて終了する。

### 2. 観点ごとにエージェントを並列で起動する

**1 メッセージ内で複数の Agent を同時に呼ぶ。** 逐次実行しない。

各エージェントに渡すもの:

- 対象ファイルのパス。**差分ではなくファイル全体を読ませる**（周辺コードとの整合を見てもらうため）
- そのエージェントが担当する観点
- 「**確信のある指摘のみ**を、`file_path:line_number` つきで返す。憶測や好みの問題は書かない」

**渡してはいけないもの:**

- なぜその実装にしたかの理由
- 検討した末に却下した代替案
- 「ここは意図的にこうしている」といった弁明

これらを渡すと、エージェントは追認するだけになる。

### 3. 観点を選ぶ

変更内容に応じて選ぶ。毎回全部やる必要はない。

| 観点 | 見るもの |
|---|---|
| **正しさ・異常系** | null 安全、例外の伝播経路、外部データの形式が想定と違う場合、境界値 |
| **ライフサイクル** | Fragment / Activity のライフサイクル、リソースやリスナーのリーク、画面回転、メインスレッドの占有 |
| **言語のイディオム** | `!!` の使用、スコープ関数の乱用、命名、可読性 |
| **設計・責務分割** | 責務が適切に分かれているか、重複がないか、テスト可能な形になっているか |
| **秘密情報** | トークンや認証情報が追跡ファイル・コミット履歴に混入していないか |

### 4. 指摘を統合して報告する

- 重複を除く
- **重要度順**に並べる（クラッシュ・データ破損 > 設計上の問題 > 可読性）
- 各指摘に `file_path:line_number` を添える
- **エージェントの指摘を鵜呑みにしない。** 誤りや的外れなものは、そう判断した理由とともに落とす。落としたことも報告する

### 5. 修正はユーザーの判断を仰ぐ

指摘を報告したら止まる。**勝手に直さない。**

どれを直すかをユーザーに選んでもらい、指示されたものだけ修正する。

## 注意

- 指摘の**件数だけ**を伝えて終わらせない。中身がわかる形で出す
- 指摘ゼロなら「ゼロだった」と明言する。無理に何か挙げない
- レビューで修正した場合、修正は作業ツリーに残す。コミットするかは `pr-create` 側の判断
