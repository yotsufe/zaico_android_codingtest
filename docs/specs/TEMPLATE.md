## 背景

**何が問題か。** 今どうなっていて、なぜ困るのか。
「あったら良さそう」で終わらせず、困りごとを具体的に書く。

現状は [spec.md](../spec.md) のどこに書かれているかを**リンクで示す**。内容を書き写さない。

## 調べたこと

**決定の根拠になる調査結果を残す。** 実 API のレスポンス、ライブラリの実測値など。
無いなら節ごと消す。

日付や件数を書くときは、**その時点の記録**だと分かるようにする。
凍結後は直せないので、受け入れ基準の前提条件にしない。

## 未決

**決まっていないことを、決まっていないと書く。** 空なら節ごと消す。

書いた本人が決めてよいものは書かない。方針の選択など、**他の人が決めるべきもの**だけを残す。
すべて埋めてから実装に入る。

## 受け入れ基準

**そのままテスト名になる粒度で書く。** 実装ではなく、外から観測できることを書く。
「使いやすくする」は基準にならない。「入力が空のとき全件を表示する」ならテストにできる。

異常系と境界を必ず含める（入力が空、通信に失敗、0 件）。

[CLAUDE.md](../../CLAUDE.md#受け入れ基準をどう守るか) の分類に従って 2 つに仕分ける。
**判断を Fragment に置けば実機でしか守れなくなる。** 寄せられるものは ViewModel 以下へ寄せる。

### 自動テストで守る

どのテストクラスが守るのかを書く。

- <入力・状況> のとき、<観測できる結果> になる

### 実機で守る

- [ ] <操作> すると <見えるもの>

## 決定

| | | |

### 引き受ける不利益

決定に代償があるなら書き残す。**将来それを覆すときの判断材料になる。**
無いなら節ごと消す。

## スコープ外

**やらないことと、その理由。** これが無いと、レビューで「ついでにこれも」が
際限なく生える。次にやるなら別の spec を起こす、と書いておく。

「ついでに直す」ものがあるなら、スコープ外にせず**受け入れ基準に入れる**。
基準に書けないものは、この変更でやらない。
