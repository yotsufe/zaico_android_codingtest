# 002: ハードコードを整理する

状態: 実装済み
PR: #19

## 背景

コード中に直書きされている値を洗い出したところ、**性質の違う 6 種類**が見つかった。
いずれも「変えたいときに何か所直すか」「多言語・ダークテーマで効いてくるか」が違う。

**実施するのは A・B・C の 3 種類。** D・E・F は調べた結果やらないと決めた
（理由は[決定](#決定)に記録）。

| # | 対象 | 箇所 | 今の困りごと |
|---|---|---|---|
| A | **今回の変更で入った Lint 指摘** | 2 | `fragment_inventory_image.xml` に `ContentDescription` と `Overdraw` |
| B | **レイアウトの色** | 3 | `#000000` 直書き。[spec.md の 6](../spec.md#6-対象環境) の「ダークテーマ未対応」の実体 |
| C | **例外メッセージの日本語** | 12 | データ層に表示文言が固定されている。**画面にそのまま出る** |
| D | **API のパス** | 2 | ホストは `api.xml` にあるがパスは直書き（**やらないと決定**） |
| E | **JSON のキー** | 9 | `"id"` `"title"` `"item_image"` など（**やらないと決定**） |
| F | **レイアウトの寸法** | 37 | `dimens.xml` には `fab_margin` の 1 件のみ（**やらないと決定**） |

## 調べたこと

### Lint の件数を誤って報告していた

`lintDebug` は成功するが、**警告が 66 件出ている**（`GradleDependency` 54 /
`SimilarGradleDependency` 6 / `AndroidGradlePluginVersion` 3 / `OldTargetApi` 1 /
`Overdraw` 1 / `ContentDescription` 1）。

これまで「Lint issue 0 件」と報告していたのは、集計スクリプトが `<issue ` （末尾スペース）で
数えていたため。実際の XML は `<issue` の直後が改行で、**1 件も数えられていなかった**。

`lintDebug` が成功するのは、すべて警告でビルドを落とす設定を入れていないから。

### C の設計はすでに半分できている

`ApiTokenMissingException` は**正しい形**になっている。

```kotlin
/** 表示する文言は文字列リソースを持つ UI 層が displayMessageOf で決める。 */
class ApiTokenMissingException : ApiException("API token is not configured")
```

内部メッセージは英語で、UI が `R.string.error_api_token_missing` に変換する。
一方 `ApiException` の他の用途は日本語を直接持ち、`displayMessageOf` の
`else -> error.message` を通って**そのまま画面に出る**。

**この 1 つの例外だけが原則に従っていて、残り 12 箇所が従っていない。**

### `@Serializable` が機能していない（別 spec で扱う）

調査中に見つけた。`Inventory` の `@Serializable` は**生成シリアライザが 0 件**で、
一度も動いていない（`Serializer for class 'Inventory' is not found`）。
`decodeFromString` / `encodeToString` の呼び出しも 0 件なので実害は無いが、
「付いているから動く」と誤解させる。

`kotlin("plugin.serialization") version "1.5.31"` と Kotlin 1.9.24 の不一致が原因と見られる。
**本 spec では触らない。** 別の主題なので 003 として起こす。

### C を変えるとテストに波及する

日本語を固定しているアサーションは 15 件あるが、**書き換えるのは 10 件**。

| 種類 | 件数 | 扱い |
|---|---|---|
| **我々がハードコードした文言** | 10 | **型で検証する形に書き換える** |
| API が返した文言（RFC 7807 の `detail` / `title`） | 4 | **そのまま維持。** API の応答を画面に出すことが検証対象 |
| テストデータ（在庫のタイトル「ねじ」） | 1 | そのまま |

書き換える 10 件は実装の写経から離れるので、テストとしてはむしろ良くなる。

## 受け入れ基準

### 自動テストで守る

**C（例外の型）**

- レスポンスが JSON でない / `data` が無い / オブジェクトでない / 配列でない /
  必須フィールドが無い / 整数でない / 範囲を超えている、のそれぞれで
  **対応する例外の型が投げられる**
- **文言ではなく型を検証する。** 文字列を固定しない
- `displayMessageOf` に分岐を足し忘れると**コンパイルエラーになる**（`when` の網羅性）
- **例外と文言、部位とラベルの対応が正しい。** `when` の網羅性が保証するのは
  「分岐があること」だけで、**対応が合っていることは保証しない**。
  在庫の文言に会社のラベルを割り当てても、対応表を検証しなければ誰も気づけない

### 実機で守る

- [x] 詳細画面の区切り線が、これまでと**同じ見た目**である（B。色は変えずに定義場所だけ移す）
- [x] API のエラー時に、これまでと同じ文言が表示される（C）
- [x] トークン未設定時の表示が変わっていない（C）

> トークンは `local.properties`（**バージョン管理外**）から `BuildConfig` に渡している。
> 不正な値を書けば API が 401 を返し、コメントアウトすれば空トークンになる。
> **追跡ファイルを 1 つも変えずに両方とも確認できる。**

## 決定

| 決定 | 理由 | 却下した案 |
|---|---|---|
| **C を sealed な例外の階層にする** | `ApiTokenMissingException` が既にこの形（内部は英語、UI が文字列リソースに変換）。**1 つだけ原則に従っていて残り 12 箇所が従っていない**状態を揃える。型で分岐でき、`displayMessageOf` の `when` の網羅性をコンパイラが検査するので、例外を足して文言を忘れることがない | 理由を enum で持たせる（`key` や `what` の付随情報に別フィールドが要る）/ 変えない |
| **E（JSON のキー）はやらない** | **真に重複しているのは `"title"` の 2 箇所だけ**（`InventoryRepository.kt` の送信ボディと `ZaicoApi.kt` の読み取り。同じ在庫の title フィールド）。`data` の 3 回は同じ関数の入口で、実際にキーとして参照しているのは 1 か所。エラーレスポンスの `title` は別のフィールド。定数化すると API のレスポンスと見比べる作業が 1 段遠くなる代償のほうが大きい | 定数に切り出す |
| **B は `@color/divider` にする**（テーマ属性ではない） | 困りごとは「`#000000` が 3 箇所に直書き」。`@color/divider` なら**3 箇所が 1 箇所に集約**され、見た目も変わらない。`?attr/colorOutline` は Material 3 が区切り線用に定めた色だが、**薄いグレーになって見た目が変わる**。`@android:color/black` は 16 進を消すだけで重複が残る | `?attr/colorOutline`（見た目が変わる）/ `@android:color/black`（3 箇所の重複が残る）/ `values-night` を足してダークテーマ対応（今回は不要と判断） |
| **D（API のパス）はやらない** | **各パスは既に 1 箇所ずつしか現れない。** リソース化しても直す箇所は同じ 2 箇所（Kotlin か XML かの違いだけ）。加えて、ホストとパスは性質が違う——ホストは**環境設定**（staging なら変わる）でリソースにする理由があるが、パスは**API の契約**で環境によらない。「ホストはリソース、パスはコード」は不統一ではなく意味のある区別だった。実際にリソース化すると `UnusedResources` が出て、配線には `ZaicoApiEndpoint` にパスを持たせる改造が要る | `api.xml` にパスを定義して `ZaicoApiEndpoint` 経由で渡す |
| **F（寸法）はやらない** | Android では余白の直書きが一般的。`dimens.xml` に出すと「レイアウトを見ても値が分からない」副作用がある。余白の体系を揃えたくなった時点で入れればよい | `dimens.xml` に spacing の体系を定める |
| **`@Serializable` の件は別 spec（003）にする** | 本 spec は既に 5 種類を扱っており大きい。別の主題 | 002 でアノテーションを外す / 002 でプラグインを直す |

## スコープ外

- **依存の更新提案 63 件**（`GradleDependency` 54 / `SimilarGradleDependency` 6 / `AndroidGradlePluginVersion` 3）。
  AGP や各ライブラリの更新は影響範囲が広く、別に扱う
- **`OldTargetApi`**（targetSdk を上げる）。同上
- **`@Serializable` が機能していない件。** 003 として別に起こす
- **ダークテーマ対応。** B は色の定義場所を移すだけ。`values-night` を足せば
  区切り線だけは直せるが、テーマ全体の検証は別の作業なので今回は入れない

## spec.md への反映

**なし。**

B は色の定義場所を移すだけで**見た目は変わらない**。ダークテーマの状況も変わらないので
[6. 対象環境](../spec.md#6-対象環境) の「未対応」はそのまま。

C も**画面に出る文言は変えない**ので記述は変わらない。
