# 001: 在庫詳細に画像を表示する

状態: 実装中
PR: —

> 最初の 1 本なので、[TEMPLATE.md](TEMPLATE.md) の書き方の見本も兼ねている。

## 背景

在庫詳細画面には「在庫画像」という欄があるが、**常に固定のプレースホルダ画像
（`drawable/no_image`）を表示している**。API が画像 URL を返していても使っていない。

そのため、画像を登録した在庫でも詳細画面では確認できない。

現状は [spec.md の 2. 在庫詳細](../spec.md#2-在庫詳細) を参照。

## 調べたこと

実 API を叩いて確認した事実。**決定の根拠なのでここに残す。**

| 項目 | 結果 |
|---|---|
| フィールド | `item_image.url`（入れ子のオブジェクト。`url` は `nullable: true`） |
| OpenAPI 上の扱い | `item_image` 自体は在庫の**必須フィールド**。`url` は null を取りうる |
| 一覧・詳細の差 | **どちらも同じ `item_image` を返す**。詳細用の追加取得は不要 |
| 画像の URL | S3 の公開 URL。**署名も有効期限も付いていない**（`X-Amz-*` なし） |
| 認証 | **不要。** `Authorization` なしで `HTTP 200` / `image/png` が返る |
| 実データ（2026-09-15 時点） | 26 件中 **1 件**だけが URL を持ち、残りは `null` |
| タイトルが空の在庫 | **API が作成を拒否する**（`400 / No Title`）。読み取り側は欠落を空文字にするので状態としてはありうるが、実機での再現手段が無い |

**画像付きの在庫が実在するので実機確認ができる。**

## 受け入れ基準

### 自動テストで守る

**「画像を出せるか」の判断まで ViewModel 以下に寄せる。** Fragment に判断を置かない
（[design.md](../design.md#各層の責務)）。

**`ZaicoApiTest`** — `item_image.url` の読み取り

- `item_image.url` に URL があれば、`Inventory.imageUrl` がその URL になる
- `item_image.url` が `null` なら、`Inventory.imageUrl` は `null` になる
- `item_image.url` が空文字・空白のみなら、`Inventory.imageUrl` は `null` になる
- `item_image` そのものが欠けていても、在庫の読み取りは失敗せず `imageUrl` は `null` になる
- `item_image` がオブジェクトでなければ、**画像なしとして扱い、在庫の読み取りは成功する**

> **`url` が数値や真偽値でも受け入れる。** 既存の `stringOrNull` は `JsonPrimitive` なら
> 種別を問わず文字列にするためで、`title` / `quantity` / `id` と同じ扱い
> （`ZaicoApiTest` の「id が文字列の数値でも受け入れる」参照）。
> ここだけ厳密にすると一貫性が崩れるので揃える。

**`ZaicoInventoryRepositoryTest`** — 一覧への影響

- **画像の形が壊れている在庫も、一覧から読み飛ばされない。** 読み飛ばし件数は増えない
  - 画像は必須の情報ではない。**画像の不備で在庫そのものが一覧から消える**のは筋が悪い
    （→ [spec.md 1.3](../spec.md#13-読み飛ばし)）

**`InventoryDetailViewModelTest`** — 画面の判断

- `Loaded` は「画像を表示できるか」を持つ。`imageUrl` が無ければ false
- 画像を表示できないとき、**タップに反応しない**ことが状態から判断できる

### 実機で守る

状態が決まったあとの**描画だけ**を確認する。

- [ ] 画像を持つ在庫の詳細で、その画像が表示される
- [ ] 画像を持たない在庫の詳細では、プレースホルダが表示される
- [ ] ~~**URL はあるが読み込みに失敗した場合、プレースホルダに戻る**~~
  **実機で決定的に再現できなかった。** 通信を切ると一覧の取得から失敗し、詳細に進めない。
  「API は成功するが画像だけ失敗する」状態を実機で作る手段が無い。
  Glide に `.error(R.drawable.no_image)` を指定していることと、同じ drawable を使う
  プレースホルダの経路が動いていることまでは確認した
- [ ] 画像の読み込みに失敗しても、ID・タイトル・数量は表示され続ける
- [ ] 画像をタップすると、ダイアログが開いて画像が画面いっぱいに表示される
- [ ] 画像を持たない在庫では、プレースホルダをタップしても何も起きない
- [ ] ダイアログは戻るキーで閉じる
- [ ] ダイアログを開いたまま画面を回転しても、画像が表示され続ける
- [ ] 詳細画面の画像を読み上げると「<タイトル>の画像」になる
- [ ] 画像を持たない在庫では「画像なし」と読み上げる
- [ ] ダイアログの画像を読み上げると「<タイトル>の画像」になる
- [ ] ~~**タイトルが空の在庫**では「在庫画像」と読み上げる~~
  **実機で確認できない。** タイトルが空の在庫は API が拒否する（`400 / No Title`）ため、
  確認用のデータを作れない。読み取り側が欠落を空文字にする以上ありうる状態だが、
  実機では再現手段が無い。分岐は 1 行で、`Context.displayMessageOf` と同じ形
- [ ] 詳細画面を離れてもクラッシュしない（`onDestroyView` 後にコールバックが届いても落ちない）

> 実機確認には**画像を登録した在庫が 1 件以上必要**。無ければ zaico の Web から登録する。
> 「調べたこと」の件数はその時点の記録であって、確認手順の前提条件ではない。

## 決定

| 決定 | 理由 | 却下した案 |
|---|---|---|
| **Glide 4.16.0** を使う | このアプリは Ktor の Android エンジン（HttpURLConnection）で通信している。Coil は **OkHttp を 2 本目の HTTP スタックとして持ち込む**。APK 増分も実測で Coil +1,393 KB に対し Glide +643 KB。さらに **Coil 3 は Kotlin 1.9.24 では metadata 2.1.0 を読めずコンパイルできない**ため、Coil を選ぶと 2.7.0 に据え置きになる。Glide は Kotlin に依存しない | Coil 2.7.0 / Coil 3 + `coil-network-ktor2` / 自前実装 |
| **`glide-compiler`（kapt）は入れない** | 生成 API（`GlideApp`）を使わず `Glide.with()` だけで足りる。kapt にプロセッサを足すとビルドが重くなる | `@GlideModule` + `glide-compiler` を入れる |
| バージョンは**版カタログに宣言する** | 他の依存がすべて `libs.versions.toml` 経由。直書きすると管理が分かれる | `build.gradle.kts` に直書き |
| **一覧には画像を出さない** | 変更範囲を詳細画面に閉じる。`item_image` は一覧のレスポンスにも含まれるので追加取得は不要だが、RecyclerView の再利用対策と行レイアウトの変更が発生し、SDD の 1 本目としては広すぎる | 一覧の各行にも表示する |
| **タップで画面いっぱいのダイアログを開く**（ズームなし） | 64dp では中身が判別できず、拡大できないと画像を出す意味が薄い。一方ズーム操作は別の要求で、画面いっぱいの表示だけで背景の困りごとは閉じる | 拡大しない / ピンチズームを入れる |
| ダイアログを **Navigation の `<dialog>` destination** にする | `DialogFragment` の見た目のまま、**Safe Args で型安全に引数を渡せる**。一覧→詳細と同じ遷移の作法になる（作成画面は `registerForActivityResult` + Intent で別の作法だが、そちらは踏襲しない） | `Bundle` を手書きして `show()` する / 新しい Fragment 画面にする / 新 Activity |
| ダイアログには **`imageUrl` と `title` を渡す**（どちらも非 null の `string`） | 開くのは画像がある場合だけなので `imageUrl` は非 null でよい。読み上げにタイトルが要る。`inventoryId` を渡して再取得すると、詳細画面が既に持っている情報を取り直すことになる | `inventoryId` を渡して ViewModel を共有する |
| 画像は **`fitCenter`** で収める | ズームが無いので、切れずに全体が見えることを優先する | `centerCrop`（縦長画像で端が切れる） |
| `Inventory.imageUrl` を **`String?`** にする。**デフォルト値 `= null` を付ける** | 「画像が無い」は異常ではなく正常な状態なので、失敗経路や番兵値ではなく型で表す。`title` / `quantity` の空文字フォールバックは「空文字が表示できる正当な値」だから成立しており、URL には当てはまらない。デフォルト値が無いと `InventoriesViewModelTest` の `Inventory(1, "ねじ", "10")` がコンパイルエラーになる | `String` にして空文字を「無い」の代用にする / デフォルト値なし |
| `contentDescription` に**タイトルを使う**。文言は **`%1$sの画像`**（「モニターの画像」） | ダイアログでは画像が唯一の中身なので、何の画像かが分からないと読み上げの意味が無い。「在庫画像」固定にしても画像の有無での出し分けは結局必要で、手間は同じまま情報だけ減る | 「在庫画像」固定 / 現状の「画像なし」固定のまま |
| **ダイアログは右上の閉じるアイコンで閉じる**（背景タップではない） | 全画面にすると、タップできる「背景」が実質無くなる。実機で上端の余白をタップしても閉じなかった。閉じ方が戻るキーだけなのは分かりにくいので、明示的なアイコンを置く | 背景タップに任せる / 画像のタップで閉じる（操作が「開く」と衝突する） |
| **ダイアログの背景を半透明のグレーにする** | 既定の白い角丸だと、背後の詳細画面が隠れて「上に重なっている」ことが伝わらない。透過画像でも背景が白だと境界が分からない | 既定の白のまま |
| **画像が無いときはタップに反応しない** | プレースホルダを画面いっぱいに見せても得るものが無い。押せそうに見えて何も起きないより、押せないほうが分かりやすい | 常にタップできてプレースホルダを表示する |
| **読み込みに失敗したらプレースホルダに戻す** | 空白のままだと壊れて見える。「画像が無い」と同じ見た目になるが、利用者にとって取れる行動は同じ | 失敗を示す専用の表示を出す |
| **`Glide.with(this)` を使い、`onDestroyView` で `clear()` する** | `Glide.with(this)` は **view ではなく Fragment のライフサイクル**に紐づくため、view の破棄では自動解除されない。だからこそ `clear()` が要る。このコードベースは `onDestroyView` で `adapter` と `_binding` を明示的に解放する作法（`InventoriesFragment` / `InventoryDetailFragment`）に揃えた | `Glide.with(requireContext())` を使う |

| **ダイアログで `DownsampleStrategy.CENTER_INSIDE` を指定する** | `fitCenter` は要求サイズが元画像より大きいと拡大してデコードする。全画面だと 498x426 が約 2 倍・メモリ 4 倍（0.85 MB → 3.4 MB）になる。ImageView が描画時に同じ倍率で拡大するので**見た目は変わらない** | 既定のまま |

| **タイトルが空なら「在庫画像」にフォールバックする** | 文言が `%1$sの画像` なので、タイトルが欠けた在庫では「の画像」とだけ読み上げられる。API のタイトルは欠けると空文字になる | 基準を取り下げる（タイトルが空の在庫は稀） |

### 引き受ける不利益

- **依存が 1 つ増える。** APK が実測で +643 KB。画像 1 枚のために画像読み込みライブラリを
  入れることになるが、キャッシュ・リサイクル・キャンセルを自前で書く代償のほうが大きい
- **Glide は純 Java で、コールバック主体の API。** `StateFlow` / `suspend` で揃えている
  このコードベースに、書き方の違うものが 1 つ混ざる
- **UI 層が通信を持つことになる。** `design.md` の責務表は Fragment に「通信」を持たせない
  と定めており、Glide の画像取得はこれに触れる。**`design.md` に例外として明記する**
  （下記「design.md への反映」）
- **`DialogFragment` はこのプロジェクトで初めて**になる。`<dialog>` destination で
  引数渡しは既存の作法に乗せられるが、ダイアログ自体のライフサイクルは新しい要素
- **画面を回転するたび Glide に投げ直される。** キャッシュに当たれば通信は起きないが、
  外れれば取りに行く。`spec.md` の「回転で読み込み直さない」は API の話で、画像は対象外

## スコープ外

- **画像のアップロード。** 表示のみを対象にする
- **一覧への画像表示。** 上記のとおり出さないと決めた
- **ピンチ・ダブルタップでのズーム。** 必要になったら別 spec を起こす
- **オフラインキャッシュの設計。** Glide 既定の挙動に任せる

## spec.md への反映

[2. 在庫詳細](../spec.md#2-在庫詳細) の画像に関する記述を差し替える。

```diff
- - 在庫画像の欄には、**API の画像ではなく固定のプレースホルダ画像**（`drawable/no_image`）を表示する。
-   読み上げ用の `contentDescription` は「画像なし」（画面に文字としては出ない）
+ - 在庫に画像が登録されていれば、その画像を表示する
+   （画像の有無の判定 → `InventoryDetailViewModelTest`）
+ - 登録されていない、または読み込みに失敗したときはプレースホルダ画像を表示する
+ - 画像の読み込みに失敗しても、ID・タイトル・数量の表示には影響しない
+ - **画像をタップすると、ダイアログが開いて画面いっぱいに表示する。**
+   背景は半透明のグレーで、背後の詳細画面がうっすら見える。
+   右上の閉じるアイコンか戻るキーで閉じる。拡大・縮小の操作はできない
+   - 画像が無い在庫では、タップしても何も起きない → `InventoryDetailViewModelTest`
+ - 読み上げは「<タイトル>の画像」。画像が無ければ「画像なし」
```

[5.2 データが欠けていたときの表示](../spec.md#52-データが欠けていたときの表示) の表は
「欠けたもの / 画面」なので、画像の行は**画面の話だけ**を書く。

```diff
  | タイトル | **空欄**で表示する → `ZaicoApiTest` |
  | 数量 | **空欄**で表示する → `ZaicoApiTest` |
+ | 画像 | **プレースホルダ画像**を表示する → `ZaicoApiTest` |
```

在庫が読み飛ばされないことは画面の話ではないので、同じ節の本文に 1 行足す。

```diff
  ID を読み取れない在庫の扱いは、画面によって違う。
+
+ 画像が読み取れない場合は、どちらの画面でも**在庫自体は表示する**
+ → `ZaicoInventoryRepositoryTest`
```

## design.md への反映

責務表の Repository / `ZaicoApi` の行はそのままに、UI 層の例外を 1 行足す。

```diff
  | Activity / Fragment | 状態の購読と描画、入力の受け渡し | 判断、通信、状態 |
+
+ UI 層が通信を持たない原則の唯一の例外が画像の読み込み（Glide）。
+ 画像は表示そのものと不可分で、ViewModel を経由させても中継するだけになるため。
```
